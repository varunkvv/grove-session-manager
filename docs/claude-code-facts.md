# Claude Code facts this project depends on

Verified on 2026-09-20 against 39 real transcripts (71,100 entries, Claude Code 2.1.221 - 2.1.278), the installed
Claude Code VS Code extension 2.1.278 bundle, the `claude` binary, and the docs at https://code.claude.com/docs.

The transcript format is internal and the docs say it changes between releases. Re-check after a Claude Code
upgrade with `pnpm oracle --strict`, which diffs our index against the Agent SDK's `listSessions()`.

Things that look surprising in the code usually trace back to a line in this file.
**Record types seen (18):** attachment, assistant, user, last-prompt, ai-title, atis-latch, bridge-session, queue-operation, mode, pr-link, custom-title, agent-name, system, file-history-snapshot, file-history-delta, permission-mode, cost-state, teleported-from. No `summary`, no `tag` in this corpus (official code still reads both).

```
{"type":"ai-title","aiTitle":"…","sessionId":"…"}
{"type":"custom-title","customTitle":"…","sessionId":"…"}
{"type":"agent-name","agentName":"…","sessionId":"…"}          equals customTitle where seen
{"type":"last-prompt","lastPrompt":"…"|null,"leafUuid":"…","sessionId":"…"}
{"type":"pr-link","prNumber":1042,"prUrl":"…","prRepository":"owner/name","timestamp":"…"}
{"type":"teleported-from","remoteSessionId":"…","branch":"main","messageCount":0}     whole file, 113 bytes, no sessionId/cwd
```

Message-bearing entries (user/assistant/attachment/system) carry: `cwd, gitBranch, sessionId, session_id, version, entrypoint, userType, uuid, parentUuid, timestamp, isSidechain, slug`. `entrypoint` = `claude-vscode` | `claude-desktop` | `cli`. Bookkeeping records carry only `type` + `sessionId`.

**Reading:** official = head 65536 + tail 65536 (one read when size <= 65536), string-scan for the LAST `"key":"` / `"key": "`, tail before head. Official display precedence: customTitle(tail) -> `<projectDir>/<sessionId>/custom-title.json` -> customTitle(head) -> aiTitle(tail) -> aiTitle(head) -> lastPrompt(tail) -> summary(tail) -> first prompt(head). Also lifts `tag` (last `"type":"tag"` in tail), gitBranch (tail then head), cwd = `relocatedCwd`(tail) ?? cwd(head), createdAt = first timestamp. Titles cut at 200 chars. Sessions whose first line has `isSidechain:true` are not listed.

**Ours:** each title field = tail ?? head, where `null` / empty / non-string counts as absent (all 4 CLI-entrypoint files open with `{"type":"last-prompt","lastPrompt":null}` - must not title as "null"; one of them becomes a fixture). customTitle = tail -> sidecar -> head. Precedence D2. Whitespace collapsed, 200 char cap, prompts indexed to 500 chars. `lastActivityMs` = max timestamp of user/assistant lines in the tail.

**Head facts:** line 1 <= 1.4KB. Head ends mid-line in 33/39 files -> cut at last `\n`. Tail starts mid-line -> drop to first `\n`. Lines up to 64KB (attachments) sit in the first 20 lines but always after the first prompt. First real prompt ends by byte 31.6KB. Two unrelated sessions share one customTitle -> row identity is the transcript path, never the title.

**First prompt:** skip the entry when `isSidechain`, `isMeta`, `isCompactSummary`, a `toolUseResult` key, any `tool_result` block, or `origin.kind === "task-notification"`. Content is a string or an array of text blocks. Per block: strip leading / trailing anchored `<system-reminder>…</system-reminder>` spans, then drop if empty or starting with `<`, `Caveat:`, `[Request interrupted`. Join survivors. Nothing survives -> next user entry. `<command-name>/x</command-name><command-args>…` -> `firstCommand = "/x args"`.

**Scan:** `projects/<dir>/<stem>.jsonl`, depth 2 only, stem without `.`, size > 0. Siblings to ignore: `<sessionId>/` (custom-title.json, subagents/, tool-results/, workflows/), `memory/`, `*.orphaned-*.jsonl`, `*.jsonl.superseded-*`. Some project dirs hold no transcript. `sessionId` == filename stem always. One sessionId per file.

**Token usage:** each assistant line carries `message.model`, `message.id` and `message.usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`). One API response is written as one line per content block, all with the same `message.id`, and later blocks can carry a larger `output_tokens` (906 of ~10k responses). Blocks of one response are usually adjacent, not always (36 cases). So: last line per id wins. `model: "<synthetic>"` marks entries Claude Code writes itself (API errors), zero spend. Usage is spread over the whole file, so it is the one thing we read in full: once, then incrementally from a saved byte offset, only whole lines. Subagent transcripts are `<sessionId>/subagents/*.jsonl` and `<sessionId>/subagents/workflows/<wf>/*.jsonl`, and count toward the session. A `cost-state` record (rare, not per turn) holds Claude Code's own `modelUsage`: its cache read / write totals match our sum exactly, its input and output are higher - it also counts side calls that never land in the transcript.

**Hooks (verified with claude 2.1.278, `-p` session):** each event's stdin is one JSON object with `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `prompt_id`, `permission_mode`. `PostToolUse` adds `tool_name`, `tool_input`, `tool_response`. `Stop` adds `last_assistant_message` and `background_tasks`. `SessionEnd` adds `reason`. Events raised by a subagent carry `agent_id` and `agent_type`; `SubagentStart` / `SubagentStop` are the only exact start and stop times a subagent has, and `SubagentStop` also carries `agent_transcript_path` and `last_assistant_message` (the agent's closing words, never the session's). Claude Code runs internal agents for `/btw` and prompt suggestions that raise `SubagentStop` too, so an `agent_id` only counts when a meta file exists for it. Docs: `PermissionRequest` fires when a tool call needs a decision, with `tool_name` and `tool_input` (an Edit's or a Write's input is the whole file, so a payload cut at 16KB keeps only the short fields near its start - `command`, `file_path` - which the parser still reads). `Notification` has `notification_type` (`permission_prompt` after ~6s, `idle_prompt` after ~60s idle, `agent_needs_input`, ...). Hooks in `.claude/settings.local.json` are honoured, settings files are watched so a running session picks up new hooks, and `async: true` keeps a hook from blocking the turn. **A running session also writes that file back** (verified 2026-09-23 by mtime across seven combos on this machine): six carried the nine-event set 0.2.7 added, written 09-22 14:28 and untouched since; the seventh, whose Claude Code session had been running since before the upgrade, was rewritten 09-23 12:27 with the old seven-event set - the copy that session loaded at startup. So a hook added while a session is running survives only until that session next persists its settings, and nothing announces the revert. The revert is not a reply to our write either: ours landed 22h earlier, so re-syncing on the file change cannot ping-pong with it. Grove watches Claude Code's own `settings.json` the same way while **Track sessions outside combos** is on, on the assumption that a session outside any combo persists its user settings the same way. That part is inferred, not observed: the revert was only seen in combo `settings.local.json` files.

**Live session registry (verified 2026-09-22, claude 2.1.278):** every live process writes `<configDir>/sessions/<pid>.json` and keeps it current: `{pid, sessionId, cwd, startedAt, procStart, version, peerProtocol, peerFeatures, kind, entrypoint, pidDomain, messagingSocketPath, name, nameSource, nameSince, status, updatedAt, statusUpdatedAt}`. `status` is `busy` or `idle`; field order varies between files. `claude agents --json` is a view over the same directory, so reading it costs no subprocess and `fs.watch` works on it. A clean exit removes the file, so one that is left behind means a crash and `process.kill(pid, 0)` is the only proof. `<pid>.<hash>.key` files sit beside them holding `{"peerToken": …}` for session-to-session messaging: never read one. A `claude -p` run writes an entry too, `status: "busy"` and `kind: "interactive"`, for as long as it is alive - Grove's own summariser calls show up in the registry for a few seconds each (harmless: their session id matches no transcript, so no row picks the state up, and the next pass retires it).

**Running `claude -p` from the app (verified by hand 2026-09-22, claude 2.1.278):** what Grove spawns to summarise an agent is
```
claude -p --model claude-haiku-4-5-20251001 --no-session-persistence --restricted --strict-mcp-config --permission-prompts none --tools ""
```
with the prompt on stdin and the cwd a throwaway temp dir (`-p` skips the workspace trust dialog, and a temp dir loads nobody's CLAUDE.md). A trivial call round-trips in ~2.5s, a real digest in ~9s. A bad `--model` exits 1 and prints to both streams, so only exit 0 counts. Each flag is load-bearing: a plain `-p` run leaves a 272KB transcript in `projects/<slug of cwd>/`, which Grove would then list as a session - `--no-session-persistence` leaves nothing. `--restricted` ignores user, project and local settings files, which is the only way Grove's own status hooks do not fire for its own calls (verified: a project `Stop` hook fired without it, not with it). `--tools ""` disables every tool. `--bare` cannot be used - it never reads OAuth or the keychain, so it is API-key only. Neither can a private `CLAUDE_CONFIG_DIR`: a fresh one prints "Not logged in · Please run /login" (and bootstraps `.claude.json` + `backups/` in it). What a run does still touch: `<configDir>/sessions/<pid>.json` while it lives, removed on exit, and `~/.claude.json`'s mtime. Nothing is added to `backups/`.

**Subagents on disk (verified 2026-09-22):** `<projectDir>/<sessionId>/subagents/agent-<id>.jsonl` with `agent-<id>.meta.json` beside it, written when the agent starts. Workflow agents nest one level further, under `subagents/workflows/<wf>/`, alongside the workflow's own `journal.jsonl`. The meta is `{agentType, description, toolUseId, spawnDepth, requestShape: "foreground"|"background", requestNonInteractive}`; a workflow agent's is only `{agentType: "workflow-subagent", spawnDepth, model}` - no description. Nothing in it records status or an end time, so: started = the meta's birthtime, last activity = the jsonl's mtime, finished = a `SubagentStop`, quiet for two minutes, or a parent session with neither a hook status nor a process in the live registry (an idle process counts: a background agent keeps working after its parent's turn ends). Reading every session's `subagents/` (meta plus a 16KB tail per agent) took 11ms cold for 54 sessions and 76 agents on one machine, so it is not cached. A single tool result reaches 40KB, so a 16KB tail can hold no `tool_use` at all. Inside an agent's transcript, a tool result line mostly carries no `toolUseResult` (4 of 246 in one agent, against every one in a session's own transcript), so a reader that wants to skip tool output before parsing has to look for the `"type":"tool_result"` block itself. Every line of an agent's transcript is `isSidechain: true`, including its prompt.

**An agent's own transcript, read whole (verified 2026-09-23 against 76 agents on one machine, claude 2.1.247 - 2.1.278):** the first `user` entry is the prompt, a plain string in every one of them. `assistant` lines carry `text`, `tool_use` (`id`, `name`, `input`), `thinking`, `server_tool_use` (the advisor) and `advisor_tool_result`; `user` lines carry `tool_result` (`tool_use_id`, `is_error`, `content` as a string or text blocks), paired to the call by id. `attachment` lines (54 of 76 in one agent are `hook_success`) say nothing about what the agent did. Every `assistant` line also has a `wireToolInputs` map keyed by tool id: what went over the wire, which for Bash has `cd <cwd> &&` put in front (152 of 246 differ in one agent) - the model's own `input` is the one to show. What Claude Code hands the parent when a foreground agent finishes (`toolUseResult` on the parent's Agent result) is the authority, and matches exactly: `content` = the text blocks of the agent's final message (the last `message.id`, when it calls no tool); `totalToolUseCount` = `tool_use` blocks, the advisor not counted; `totalTokens` = input + output + cache read + cache write of the LAST response alone - the context it ended with, not a sum (71,212 for an agent whose responses sum to 599,091); `totalDurationMs` = first to last timestamp in the agent's file, within a few ms. A background agent's Agent result is only `async_launched`, so for those the agent's own file is all there is. How an agent ends badly, as seen: a `model: "<synthetic>"`, `isApiErrorMessage: true` line ("API Error: ...", `error: "server_error" | "invalid_request" | ...`), or a trailing `[Request interrupted by user]` user entry, sometimes right after a tool result that says the tool use was rejected. `stop_reason` cannot tell: it is null on some last lines. Later non-result `user` entries are `isMeta` notes from Claude Code (image sizes, a retry after a cut-off stream) and messages sent to a running agent (`origin.kind: "coordinator"`, text starting "The coordinator sent a message while you were working:"). Every `thinking` block on that machine was redacted - an empty `thinking` and a signature. Not true of newer ones: on 2026-09-23 an agent on `claude-opus-5-5` had 15 of its 119 `thinking` blocks with text in them (160-300 characters each), the rest redacted. None of the 76 had `spawnDepth` above 1 or called Agent itself, so a nested agent is unverified: the code assumes it is linked like any other, through its meta's `toolUseId`. A workflow's `journal.jsonl` holds `{type: "started"|"result", key, agentId, result?}`, and the parent's Workflow result carries `toolUseResult.{runId, workflowName, summary}` with `runId` = the `workflows/<wf>/` directory name.

**A session's own conversation, read whole (verified 2026-09-25 against 68 main transcripts on one machine, claude 2.1.247 - 2.1.281; sizes p50 1.1MB, p90 8MB, max 107MB):** a turn starts at a `user` line that is a person's prompt, a slash command, or a background task's news. A prompt has `origin.kind: "human"`; lines from before `origin` existed have none, and are a prompt when they are not `isMeta`, not a `tool_result`, not `isCompactSummary` and not a command envelope, command output or task notification. Its text blocks carry the editor's context in front (`<ide_opened_file>`, `<ide_selection>`) and reminders around it, stripped per block the way the first prompt is; one that is nothing but that context still starts a turn. Pasted images are `{type: "image", source: {type: "base64", …}}` blocks, followed by an `isMeta` "[Image: original WxH…]" note. A prompt typed in plan mode has `permissionMode: "plan"`. A slash command is `<command-name>/x</command-name>` + `<command-message>` + `<command-args>` (for a skill `<command-message>` comes first), preceded by an `isMeta` `<local-command-caveat>` line; its output is the next `<local-command-stdout>` user line or a `system` line with `subtype: "local_command"`, and one that expands into a prompt writes the expansion as an `isMeta` user line. A background task finishing while the session sat idle is a user line with `origin.kind: "task-notification"` and `<task-notification>` + `<task-id>`, `<tool-use-id>`, `<status>` (completed, failed, killed, stopped), `<summary>` (html-escaped). Inside a turn it is an agent's life (above): `assistant` blocks and `tool_result` user lines, the answer being the text of the final message. Something typed while it worked (129 of them) is an `attachment` of type `queued_command` with `commandMode: "prompt"`, `origin.kind: "human"` and the text in `prompt` - never written again as a user line; twice the same text as the turn's own prompt, a double submit. `commandMode: "task-notification"` is a background task finishing mid-turn. `system` lines: `api_error` with `error.formatted` ("Connection dropped (ECONNRESET)"), `retryAttempt`, `maxRetries` - a retry that then worked is followed by the assistant carrying on; `turn_duration` with `durationMs` (newer background sessions only); `compact_boundary` with `compactMetadata.{trigger: "auto"|"manual", preTokens, postTokens, preservedSegment}`, followed by an `isCompactSummary` user line ("This session is being continued…"). An automatic compaction lands in the middle of a turn and the assistant goes on after it with no prompt; `/compact` writes its boundary and summary first and its command line after them. After a compaction Claude Code writes the preserved segment again: the same uuids with a different `parentUuid` / `cwd` and the timestamps of the originals (in one 107MB file, 134 lines 2,400 lines after their originals, attachments between them too) - so lines are deduplicated by uuid, and the newest timestamp is a max, not the last line's. Walking `parentUuid` from the last line misses about half of a conversation (attachments sit in the chain, parallel tool results are siblings), so file order is the order. No rewind (an edited prompt) was found. The `cwd` can change between turns (one session worked in four repos). `toolUseResult` beside a tool result is the structured version: Bash `{stdout, stderr, interrupted, isImage, noOutputExpected, returnCodeInterpretation?, backgroundTaskId?, persistedOutputPath?, bashEditDiff?}`, Edit `{filePath, oldString, newString, originalFile, replaceAll, structuredPatch, userModified}`, Write `{type, filePath, content, originalFile, structuredPatch}` (`structuredPatch` hunks are `{oldStart, oldLines, newStart, newLines, lines}`, a unified diff; `originalFile` is the whole file), Agent `{agentId, status, prompt, totalTokens, totalToolUseCount, totalDurationMs, …}`, AskUserQuestion `{questions, answers}` with `answers` keyed by the question's text, ExitPlanMode `{plan, filePath, isAgent}` when approved - turned down, it is a string, the result `is_error`, and the person's words follow "reason for the rejection:" or "the user said:". A result too big to keep is `<persisted-output>` + "Output too large (42.6KB). Full output saved to: <projectDir>/<sessionId>/tool-results/<id>.txt" + a 2KB preview (Bash also sets `persistedOutputPath`). No `TodoWrite` call is on this machine: newer Claude Code plans with `TaskCreate` (`{subject, description, activeForm}`) and `TaskUpdate`, so the TodoWrite checklist (`input.todos[].{content, status}`) is built from the documented shape, not an observed one. Most of the lines are noise to a reader: hook results and other attachments, `stop_hook_summary`, and the metadata written again and again. Dropping those on their first bytes, before decoding, folds the 107MB file in ~140ms.

**Background sessions (verified 2026-09-23, claude 2.1.280 - 2.1.281, with haiku in a trusted test folder):** `claude --resume <id> --bg -- <prompt>` on a session nothing is running continues it under the same session id and transcript (the new lines carry `entrypoint: "cli"`); on a session something is running it starts a copy and says so (per the 2.1.257 changelog, not observed). The process tree is daemon -> `claude bg-pty-host` -> `claude bg-spare`, a child of no terminal or editor; a panel session is a child of `Code Helper (Plugin)` and goes with the window. `claude agents --json --all` (~170ms) lists interactive and background sessions: a background row is `{pid?, id, sessionId, cwd, kind: "background", name, status?, state, waitingFor?, startedAt}`, an interactive row has no `id` and no `state`. `state` is `working` | `blocked` | `done` | `failed` | `stopped`; `pid` and `status` (`busy` | `waiting` | `idle`) only while a worker is alive, and the supervisor lets a finished or waiting worker go after about an hour unattached, so "held" is a pid, never a state. `waitingFor` (`permission prompt`, `input needed`, `sandbox request`, `worker request`, `dialog open`) only while `status` is `waiting`. The registry file of a background session has `kind: "bg"`, `entrypoint: "cli"` and `status`, never `state`. `attach`, `logs` and `stop` take the short `id` only - the full uuid gets "No job matching '<uuid>'" and exit 1 (the id was the uuid's first 8 characters every time, but nothing promises it). A foreground `claude --resume <id>` while the supervisor holds the session refuses: "Session <id> is running as a background session (<short>). Run `claude attach <short>` to open it, or `claude stop <short>` first to resume it here."; after `claude stop` (which prints `stopped <short>` and drops the pid within a second, the state kept as it was) it resumes in place. `claude --bg` prints `backgrounded · <short>` (then ` · <name>` and four help lines). `--` ends option parsing, so a prompt after it can start with a dash, and `--name=<name>` keeps a leading dash as part of the name. Since 2.1.281 `--bg` and `--resume --bg` exit 1 in a folder that has not passed the CLI's trust prompt when nothing is interactive: "Workspace not trusted. Run `claude` in <dir> once and accept the trust prompt, then retry." on stderr, before the session is even looked up; run in a terminal, the same command asks for trust first (per the 2.1.281 changelog, not observed yet). A background session runs with the environment it was dispatched with: dispatched from a Finder-like env its Bash had no node, pnpm or gh, and dispatched with the login shell's env its worker's PATH was that PATH exactly. A combo's hooks fire inside a background session (its `live-status.json` went running -> waiting on its own), and edits in a combo root (not a git repo) land in place, no `.claude/worktrees/`. The daemon exits on its own soon after its last session is removed. `claude logs` is raw ANSI terminal output: the transcript is still the source. Docs: https://code.claude.com/docs/en/agent-view - a reboot stops background sessions; within 48 hours a running one shows as `failed` (attach or reply restarts it), past that as `stopped`.

**Slug (byte-identical in CLI and extension):**
```js
function slug(cwd){ const s = cwd.replace(/[^a-zA-Z0-9]/g,'-'); if (s.length <= 200) return s;
  let h = 0; for (let i = 0; i < cwd.length; i++) h = ((h << 5) - h + cwd.charCodeAt(i)) | 0;   // over the ORIGINAL cwd
  return `${s.slice(0,200)}-${Math.abs(h).toString(36)}` }
```
Input is `realpathSync`'d and NFC-normalised on darwin. Never reverse a slug.

**Claude Code VS Code extension 2.1.278:** activation `onStartupFinished`, no `onUri`. `registerCommand("claude-vscode.primaryEditor.open", async (session, prompt) => createPanel(…))`. URI `/open` reads only `session` + `prompt`, validates session as 1-200 chars without `/ \ .. NUL`, then calls that command. An already-open session tab is revealed and the prompt dropped. cwd = `workspaceFolders[0]` (realpath + NFC), other roots -> additionalDirectories for the spawned process. Session list scope root = `workspaceFolders[0]`. Its keybindings: `alt+k`, `cmd+escape`, `cmd+shift+escape`, `cmd+alt+k`, `ctrl+alt+f`, `cmd+shift+t`, `cmd+n`. Docs: "The session must belong to the workspace currently open in VS Code. If the session isn't found, a fresh conversation starts instead." / "If VS Code is already running, the URL opens in whichever window is currently focused."

**A new conversation from outside (read from the extension source, 2.1.282, 2026-09-25):** `primaryEditor.open` and the `/open` URI still take only `(session?, prompt?)` - nothing else (model, permission mode, effort, system prompt) can be passed in. `/open` with no `session` param calls the command with `undefined`. `createPanel(undefined, prompt, …)` skips the "already open" lookup and makes a new webview panel; the page gets `data-initial-prompt` and no `data-initial-session`. Its boot resolver (`sessionToResume` from the webview's saved state, `initialSession`, `initialPrompt`) then lands on `fresh_with_prompt` (or `blank`): `createSession()` and the prompt set as the new session's `initialPrompt`, which fills the input box. The prompt is NOT sent. The one assumption this rests on: a panel made by `createWebviewPanel` has no saved state, so `sessionToResume` is undefined and it never reopens the last conversation - only a panel VS Code restores through the serializer has state. If that changes, an undefined session would resume instead. Not seen in a real window, only read.

**CLI flags a new session can start with (`claude --help`, 2.1.281):** `--model <alias|name>` (aliases `fable`, `opus`, `sonnet`, `haiku`), `--permission-mode` (`acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), `--effort` (`low`, `medium`, `high`, `xhigh`, `max`), `--append-system-prompt <text>`, `-n/--name <name>`. `--system-prompt-snapshot on` (the default) renders the system prompt, an appended one included, on the conversation's first request and reuses that record verbatim on every later request and resume, "even when a later launch passes different text", until a compaction - so an appended prompt is fixed at the start of a conversation, and a `--resume` cannot change it.

**Those flags on a real background session (verified 2026-09-25, claude 2.1.281, a trusted test folder, dispatched through Grove's own `parseNewSession` -> `backgroundArgs` -> `LoginEnv` -> `BackgroundService.dispatch`):** `claude --bg --model haiku --permission-mode plan --effort low --append-system-prompt=<policy> --name=<name> -- <prompt>` printed `backgrounded · 73148839 · grove new-session check` (and "Starting background service…" on stderr, ~4s, the daemon was not up). `claude agents --json --all` then had `{id: "73148839", kind: "background", name: "grove new-session check", state: "done", status: "idle"}` - no model, mode or effort on the row. The transcript is where they show: the `permission-mode` records and the user line say `plan`, the assistant line carries `effort: "low"`, and the whole rendered system prompt is in an `attachment` of type `prompt_snapshot` (`systemPrompt`, 17 strings), with the appended policy at its end - the reply quoted its last sentence word for word. The model was `claude-sonnet-5`, not Haiku: the changelog says "Haiku 4.5 automatically uses Sonnet in plan mode, and Haiku for execution", and a `-p --model haiku --permission-mode plan` run bills both models. Without plan mode, `claude --bg --model haiku` and `--model=haiku` both ran on `claude-haiku-4-5-20251001`. Asked for plain text in plan mode, the session answered and ended `done` - it did not stop on ExitPlanMode. `claude stop` + `claude rm` cleared the rows; the transcripts stay, and the transient daemon kept running with a spare worker right after.

**VS Code URI routing:** `openExternal(vscode://…)` -> renderer -> main process. `windowId=<n>` in the query routes to that window, else the last active one. `vscode.env.asExternalUri(appSchemeUri)` appends this window's `windowId`. Use `vscode.env.uriScheme` (Cursor's is `cursor`). `anthropic.claude-code` is not in `trustedExtensionProtocolHandlers` -> one-time modal.

**Docs:** `claude --resume <id>` works from any directory since 2.1.223, but reports not-found when copies exist in several project dirs. `claude --resume <transcript-path>` works. `/cd` and Claude-created worktrees relocate the transcript. `claude-cli://open` has only `q`, `cwd`, `repo` - no resume param. Retention 30 days (`cleanupPeriodDays`, min 1), desktop transcripts exempt. Panel auto-archive 14 days (enum 0/1/2/7/14). `settings.local.json` applies without the trust step unless git-tracked. Lists merge across settings scopes. `additionalDirectories` from settings never loads CLAUDE.md / rules / skills. Subdirectory CLAUDE.md loads on demand. `claude agents --json` is the supported liveness surface (not used in v1). Agent SDK 0.3.278: `listSessions({dir?, limit?})` -> `{sessionId, summary, lastModified, fileSize, customTitle, firstPrompt, gitBranch, cwd, tag, createdAt}`.

**A typical macOS install:** VS Code `/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code`, extensions `~/.vscode/extensions` (`extensions.json` array + `.obsolete` map). Cursor `/Applications/Cursor.app/Contents/Resources/app/bin/code`, `~/.cursor/extensions`. claude `~/.local/bin/claude`. git prints realpaths in porcelain (`/private/tmp/...`), and a PATH can put a version-manager shim ahead of the real git - the resolver skips anything under `/shims/`.

**Fixtures** in `packages/core/test/fixtures/` are real transcripts with every string replaced (structure kept, byte lengths preserved so offsets survive): `tail50k` (first ai-title at byte 50,841 - past a 48KB head, inside the 64KiB one), `middle` (a single ai-title in the unread middle of a large file - falls back to the first prompt), `twotitles` (several ai-titles, last wins), `sidecar` (custom-title + sidecar file + agent-name), `command` (a CLI session that is only slash commands), `idefirst` (an `<ide_opened_file>` block before the typed text), `stub` (a 113-byte teleported-from marker). `timeline/` holds whole agent transcripts next to the parent lines that started them (`scripts/redact-agents.ts`: ids rewritten consistently so calls still pair with results, the same string always the same filler so a parent's copy of a result still equals the agent's, long strings capped): a finished Explore agent, a workflow agent with its journal, one that died on an api error, and two interrupted ones. `conversation/` is a 3,124-line stretch of a real 107MB session (`redact-agents.ts --lines`, 1,211 of its lines kept: most hook results and metadata left out, strings cut at 60 characters, the usage breakdown cut to its four counts, and the envelope every line repeats - slug, branch, request and parent ids - dropped): three compactions, the preserved segment written again after one of them, slash commands and their output, background tasks finishing, a question with answers, three plans turned down and one approved, pasted images, a message typed mid-turn, and one background agent's own transcript.

## Electron, not Claude Code

**`fs.watch` on a directory misses changes made in the first moments after it returns (macOS).**
Verified 2026-09-23: libuv backs a directory watch with FSEvents, and the stream is started on
another thread, so `watch(dir, cb)` followed immediately by a write in that dir can deliver nothing
at all - reliably so on a loaded machine (the whole test suite running). It is not a delay, the
event never arrives. So nothing may assume a watch is live the moment it is created: the status
hook re-sync also runs on window focus, and the test for it touches the file until an event comes
back before it begins. A watch on a single file goes through kqueue instead and dies with the inode,
which is why every watch here is on the directory, filtered by name.

**`nativeTheme.themeSource` does not reach the renderer's `prefers-color-scheme` in Electron 44.**
Verified on 44.4.3: main reported `shouldUseDarkColors: true` while the page still matched
`(prefers-color-scheme: light)`. So the app pins a chosen appearance with a `data-theme` attribute
on `:root` (carried on the page URL, so the first frame is already right) and keeps `themeSource`
only for the window frame and the native menus. Re-check on an Electron upgrade: if it starts
working, the attribute can go.
